# 작업표시줄 고양이 실패·복구 감사

상태: **Active recovery record**  
최종 갱신: 2026-07-10  
적용 범위: 작업표시줄 고양이의 원화, 포즈, 입력 반응, 완료 표시, 드래그 동작

이 문서는 실패를 정당화하기 위한 기록이 아니다. 다음 작업자와 다음 대화가 같은 실패 경로를 다시 선택하지 못하도록 증거, 원인, 금지 경로, 현재 결정과 검증 게이트를 고정한다.

## 1. 현재 판정

- v31 16프레임 연속 재생: **Rejected** — 심한 좌우 이동과 과속 유휴 동작.
- v2 요리사·냄비·도구 6포즈: **Rejected by user** — 뒤집개 공중부양/이탈과 국자 손 관통.
- v3 무도구 냄비 두드리기 실험: **Rejected by user** — 접촉 구조는 안전해졌지만 요리사 설정과 행동의 의미가 뜬금없음.
- 서비스 벨 아이디어: **Rejected by user** — 현재 캐릭터·게임 방향과 맞지 않음.
- 두 반죽 v1 중립: **Superseded by user direction** — 사용자가 반죽을 하나로 요청했으므로 참고 원본만 보존하고 런타임에는 다시 쓰지 않는다.
- 한 반죽 치대기 v2: **Implemented, not verified** — 한 덩어리 중립과 국소 좌/우 누름·깜빡임을 합성한 2 × 2 아틀라스를 만들었고 런타임 연결을 진행했다. 실제 로컬 페이지 연속 재생에 대한 사용자 승인은 남아 있다.

## 2. 실패 증거

- 그러나 요리사 고양이가 냄비 가장자리를 봉고처럼 두드리는 행동은 직업·복장·소품과 자연스럽게 연결되지 않았다.
- 이 실패는 “오류가 적게 나오는 그림”과 “게임에 맞는 좋은 아이디어”가 같은 것이 아님을 보여 준다.
- 이 후보는 런타임에 연결하지 않았으며 재사용 금지 실험으로만 보관한다.

## 3. 왜 실패했는가

### 3.1 상호작용 개념보다 완성 아틀라스를 먼저 생성함

무엇을 왜 하는 고양이인지 승인받기 전에 6개 상태를 한 번에 만들었다. 그 결과 예쁜 개별 컷을 얻는 데 집중했고, 프레임 사이의 행동 논리와 소품 연속성이 뒤로 밀렸다.

### 3.2 생성 모델이 취약한 접촉 구조를 핵심 동작으로 선택함

얇고 긴 뒤집개·국자, 열린 앞발, 손잡이, 냄비 테두리와 수프가 한 영역에서 겹쳤다. 이 조합은 손가락 수, 그립, 앞뒤 가림, 도구 지지점을 동시에 정확히 유지해야 하므로 생성 결과가 안정적이지 않았다.

### 3.3 전체 프레임을 각각 다시 그리게 함

몸, 얼굴, 팔, 도구, 냄비, 수프, 조명까지 상태마다 재해석됐다. 정렬 스크립트는 위치를 맞출 수 있지만 해부학, 접촉, 하이라이트와 소품 형태의 변화를 고칠 수 없다.

### 3.4 품질 게이트가 수치와 축소 접촉표에 치우침

기존 검사는 중심 편차, 바닥선, 알파, 마젠타 잔류와 전체 128px 판독성은 확인했다. 그러나 다음 항목이 명시적 즉시 탈락 조건에 없었다.

- 열린 앞발을 손잡이가 가로지르는가
- 활성 손과 도구 사이에 투명 틈이 있는가
- 도구가 잡히거나 고정되지 않은 채 허공에서 끝나는가
- neutral↔key 왕복에서 도구를 버리거나 순간이동하는 것으로 읽히는가
- 직업·복장·행동이 한눈에 같은 의미로 읽히는가

### 3.5 구조적 오류를 없애면서 의미까지 없앰

도구를 제거한 v3는 기하 문제를 해결했지만, 냄비를 타악기처럼 사용하는 새 의미 문제를 만들었다. 기술적 안전성만 최적화하면서 제품 콘셉트 적합성을 별도 게이트로 두지 않은 결과다.

## 4. 다시 사용하지 않을 경로

- 독립적으로 생성한 6개 전신 포즈를 한 번에 런타임 후보로 만드는 방식.
- 얇은 손잡이 도구를 열린 앞발로 잡거나 놓는 입력 반응.
- 손, 긴 도구, 냄비 림과 액체가 같은 작은 영역에서 교차하는 구도.
- 이미지 생성 프롬프트의 “정확히 잡는다” 문장을 실제 접촉 검증으로 간주하는 방식.
- 숫자 정렬·알파·해시 통과를 해부학·행동 의미의 합격으로 확대 해석하는 방식.
- 같은 접촉 결함에 세 번째 이상 유사 프롬프트를 계속 쓰는 방식.
- 중립 기준 원화의 사용자 승인 없이 상태 아틀라스부터 제작하는 방식.

## 5. 채택한 복구 원칙

1. 먼저 행동 의미를 텍스트와 한 장의 중립 원화로 승인받는다.
2. 128px 밝은/어두운 배경에서 중립 실루엣, 복장, 작업대와 접촉면을 먼저 확정한다.
3. 몸·복장·작업대·고정 소품은 승인 원본 픽셀을 모든 상태에서 그대로 재사용한다.
4. 좌우 팔/앞발, 눈, 입만 별도 레이어로 분리한다.
5. 넓고 단순한 접촉면을 사용하고 얇은 탈착 도구와 액체 접촉은 피한다.
6. 완료 표시는 포즈가 아니라 별도 UI 레이어로 표시하며 입력 반응을 멈추지 않는다.
7. 한 결함이 두 번 반복되면 프롬프트를 더 쓰지 않고 레이어 구조나 상호작용 자체를 바꾼다.
8. 내부 QA는 참고 증거일 뿐이며 사용자의 시각적 거절이 최종 합격을 즉시 무효화한다.

## 6. 반죽 치대기 타당성 검토

### 6.1 결론

제빵 고양이가 반죽을 치대는 개념은 요리사 복장, 고양이의 꾹꾹이 행동, Bongo Cat식 좌우 입력 반응, 확장 게임의 음식 생산을 자연스럽게 연결한다. 아이디어 적합성은 높다.

다만 **6개 전신 프레임을 다시 생성하면 성공 전망이 낮다.** 반죽이 수프·팬케이크·그릇처럼 바뀌거나, 손과 반죽 접점·몸·작업대가 프레임마다 흔들릴 가능성이 남는다. 한 장의 마스터와 결정론적 2D 레이어 리그를 사용할 때만 유력 후보로 본다.

| 기준 | A. 6개 전신 프레임 생성 | B. 고정 마스터+국소 생성 편집 | C. 승인 마스터+결정론적 2D 리그 |
|---|---|---|---|
| 테마 적합성 | 보통 | 높음 | 높음 |
| 손·반죽 접촉 신뢰성 | 낮음 | 보통 | 높음 |
| 프레임 연속성 | 낮음 | 높음, 단 마스크 밖 오염 위험 | 높음 |
| 128px 좌우 반응 판독 | 보통 | 높음 | 높음 |
| 생성 재시도 위험 | 높음 | 보통 | 낮음 |
| Unity 포팅·튜닝 | 보통 | 높음 | 높음 |
| 판정 | 사용 금지 | 제한적 보조 | **권장** |

### 6.2 권장 C 구조

- 고정 마스터: 몸, 머리, 요리사 복장, 나무 작업대, 반죽 기본형.
- 분리 레이어: 왼팔+왼앞발, 오른팔+오른앞발, 눈, 입.
- 반죽: 무광 베이지색의 폭 40px 이상인 넓은 타원. 액체 반사, 그릇 테두리, 주황 건더기를 사용하지 않는다.
- 레이어 순서: 몸통 → 작업대 뒤판 → 반죽 본체 → 앞발 → 반죽 접촉 릿지/작업대 앞판.
- 키 입력: 현재 neutral이 이미 반죽에 접촉하므로 첫 검증은 해당 앞발만 128px 기준 3–4px 내린다. 더 큰 이동은 접촉 검증 뒤에만 허용하며, 반대 앞발과 몸은 0px 이동한다.
- 반죽 반응: 새 그림을 생성하지 않고 피벗 기준 `scaleY` 8–12% 감소, `scaleX` 5–8% 증가 후 복귀한다.
- 접촉: 손 아래 1–2px의 그림자 또는 전경 릿지를 유지해 공중부양과 관통을 동시에 방지한다.
- 깜빡임·웃음: 얼굴 레이어만 바꾼다.
- 졸기: 얼굴과 머리만 1–2px 움직이며 몸·작업대·반죽은 고정한다.
- 밀대, 국자, 그릇, 가루 봉지 같은 탈착 도구는 첫 버전에서 사용하지 않는다.
- 밀가루 `퐁` 효과가 필요하면 원화에 굽지 않고 별도 짧은 FX 레이어로 사용한다.

### 6.3 생성 전에 적용할 즉시 중단 조건

- 승인된 neutral 원화와 128px 밝은/어두운 미리보기가 없음.
- 다시 6포즈 전신 시트부터 생성하려 함.
- 앞발이 정확히 2개가 아니거나 소매에서 분리됨.
- 손과 반죽 사이에 투명 틈이 있거나 손이 반죽·작업대 내부로 들어감.
- 국소 편집에서 마스크 밖 마스터 픽셀이 변경됨.
- 몸·작업대·반죽이 상태 사이 1px보다 많이 이동하거나 형태가 바뀜.
- 반죽이 수프, 팬케이크, 그릇 또는 북처럼 읽힘.
- 128px에서 확대하지 않으면 좌우 누름을 구분할 수 없음.
- neutral↔left/right 왕복에서 전체 실루엣이나 하이라이트가 깜빡임.
- 동일한 손·접촉 결함이 두 번 반복됨.

## 7. 현재 검증 공백

- 두 반죽 neutral은 사용자의 한 반죽 요청으로 폐기 대상이 아니라 참고 전용으로 전환됐다.
- 현재 v2는 완전한 clean plate/관절 리그 대신, 승인 방향의 한 반죽 중립 마스터 위에 선언된 좌/우 앞발·반죽 및 눈 마스크만 합성하는 제한된 파이프라인을 사용한다. 마스크 밖 픽셀 동일성은 검증됐지만 실제 Unity 본/레이어 리그는 아직 아니다.
- 드래그와 완료 표시 분리 코드는 자동 테스트를 통과했지만 사용자의 실제 `file://` 조작 승인은 남아 있다.
- 실제 Unity 리그, Windows 전역 입력, Steam 오버레이 동작은 아직 구현하지 않았다.

## 11. 2026-07-10 사용자 판정 — 정자세·손만 움직이는 기계

사용자가 빠른 반죽 게임감 v1을 실제로 본 뒤 “고양이가 살아있는 것 같지 않고, 정자세로 서서 손만 움직이는 기계 같다”고 정확히 판정했다. 이는 티켓이나 타이머의 문제가 아니라 캐릭터 생명감 목표에 대한 명시적 거절 신호다.

### 관찰

- 머리, 시선, 귀, 어깨, 몸통, 허리와 작업대가 모든 작업 상태에서 정면 중앙 정렬로 고정돼 있다.
- 바뀌는 핵심 픽셀은 한쪽 앞발·팔과 해당 반죽 영역이며, 눈 깜빡임과 밀가루 퍼프는 별도의 장식 신호다.
- 앞발이 눌러도 반대쪽 어깨, 몸의 중심, 고개·시선과 표정이 그 힘에 반응하지 않는다.
- 진행 티켓과 자동 간격은 “작업 중”이라는 정보는 전달하지만 캐릭터가 스스로 의도하고 힘을 쓰는 인상은 만들지 못했다.

### 원인 가설과 증거 수준

- **확정된 사용자 관찰:** 정면 정자세와 손만 움직이는 결과가 기계처럼 보인다.
- **강한 구조적 원인 가설:** 이전 전신 흔들림 실패를 막기 위해 몸·무대 안정성을 “몸 전체 정지”로 과도하게 구현했다. 그 결과 운동 사슬의 예상 동작, 무게 이동, 접촉과 복귀가 사라졌다.
- **아직 검증되지 않은 해결 가설:** 작업표시줄 접촉 루트와 작업대는 고정하되, 승인된 비대칭 작업 마스터에서 머리/시선, 귀, 꼬리, 어깨, 상·하완/앞발, 얼굴과 반죽 접촉 변형을 계층 레이어로 움직이면 흔들림 없이 생명감을 만들 수 있다.

### 2026-07-11 국소 결함 수정과 UI/UX 설계의 혼동

사용자는 Codex의 실제 작업이 UI/UX를 구상한 것이 아니라 적당한 품질에서 요소가 삐져나가지 않는지만 확인하는 것처럼 보인다고 지적했다. 이는 단순 취향 피드백이 아니라 현재 제작 방식에 대한 정확한 실패 진단이다.

#### 실패 원인

- 기존 HTML의 3열 카드 보드를 전제로 고정하고, 화면이 무엇을 위해 존재하는지와 사용자가 어디부터 무엇을 해야 하는지를 정의하지 않았다.
- 합격 기준을 `잘리지 않음`, `이미지가 로드됨`, `테스트 통과`, `자산이 내장됨` 같은 결함 방지 항목에 치우쳤다. 이는 하한선이지 UI/UX 품질 기준이 아니다.
- 고양이, 식당, 레시피, 생산, 파견을 같은 화면에 나란히 배치했지만 이들이 `고양이 선택 → 행동 선택 → 결과 확인 → 작업표시줄 변화`로 이어지는 사용 흐름을 만들지 않았다.
- 모든 카드와 버튼이 비슷한 시각 무게를 가져 초점, 주 행동, 다음 행동, 상태 변화가 분리되지 않는다. 베이지 카드 격자는 기능을 담지만 이 게임만의 정체성이나 감정적 경험을 만들지 못한다.
- 실제 화면을 본 뒤에도 구조를 재설계하지 않고 crop, 폭, 행 높이만 고쳤다. 따라서 한 결함을 고칠 때 다른 밀도·비율 결함이 드러나는 반응형 패치 루프가 생겼다.

#### 중단할 경로

- 현재 3열 카드 보드를 그대로 두고 여백, 크기, 아이콘, 미디어 쿼리만 계속 보정하는 방식.
- 자동 테스트와 자산 해시를 디자인 품질의 대리 지표로 사용하는 방식.
- 한 화면에 모든 시스템을 동시에 보여 주면 깊이 있어 보인다고 가정하는 방식.

#### 다음 설계 경로

1. 화면의 목적을 한 문장으로 정한다. 예: `오늘 고양이가 만든 것과 다음에 시킬 일을 10초 안에 결정하는 관리 화면`.
2. 작업표시줄 고양이에서 열린 메뉴로 들어오는 순간의 사용자 질문과 첫 행동을 정한다.
3. 고양이·식당·레시피·생산·파견의 정보 구조와 전환 흐름을 먼저 만든다. 동시 노출이 필요하지 않은 시스템은 탭/단계/드릴다운으로 분리한다.
4. 코드 전에 서로 다른 2~3개 저해상도 와이어프레임을 실제 목표 창 비율로 비교하고, 초점·행동 순서·한눈 이해를 사용자에게 승인받는다.
5. 선택된 구조에만 IP 분위기, 일러스트 사용 방식, 타이포그래피, 색·간격·버튼 상태의 시각 시스템을 적용한다.
6. 한 화면을 실제 크기로 구현하고 `무엇을 먼저 보게 되는가`, `다음 행동이 명확한가`, `행동 결과가 작업표시줄 고양이로 돌아오는가`를 시각·동작으로 검증한 뒤 확장한다.

현재 menu-v1의 상태는 **Rejected as UI/UX direction**이다. 기능적 수정과 자산은 참고로 보존하지만 현 구조를 완성 방향으로 다듬지 않는다.

### 2026-07-11 기본 표현 품질을 세 번 연속 놓친 원인

사용자가 전체 문제를 대표하는 네 크롭을 제공했다.

- `assets/menu-v1/qa/ui-quality-failure-item-tile.png`: 불투명한 크림 사각형이 노란 장비 카드 안에 그대로 보여 이미지가 통합된 아이콘이 아니라 붙여 넣은 파일처럼 보인다.
- `assets/menu-v1/qa/ui-quality-failure-cook-button.png`: 같은 음식 타일을 역할 변환 없이 `요리` 행동 버튼에 다시 사용하고, 컨트롤은 일반 웹 버튼처럼 보인다.
- `assets/menu-v1/qa/ui-quality-failure-production-row.png`: 서로 다른 생산 시설이 동일한 초록 막대와 동일한 `받기` 버튼을 반복해 상태·완료·보상 차이를 전달하지 못한다.
- `assets/menu-v1/qa/ui-quality-failure-toolbar.png`: 선 굵기·채색·형태 언어가 다른 아이콘을 모두 같은 둥근 사각 버튼에 넣어 게임의 내비게이션보다 웹 도구 모음처럼 보인다.

이 문제를 놓친 이유는 화면 접근 제한이나 자료 부족이 아니다. 첫 사용자 스크린샷에 이미 대부분 보였고 Codex가 볼 수 있었다. 검수자가 각 턴의 지시를 `폭`, `배경`, `초상`, `아이콘 크기` 같은 단일 결함으로 좁혀 보고, 전체 화면을 다시 자유롭게 비평하지 않았다. 생성 자산을 이미 작업한 결과물이라는 이유로 배제보다 통과 근거를 찾는 확증 편향도 생겼다. 자동 테스트·자산 해시·내장 수·무오버플로는 엔지니어링 하한선인데 이를 시각 품질 근거처럼 반복 보고했다. 그 결과 `선명하게 로드된 저품질 합성`을 성공으로 오판했다.

이번 실패는 UX 구조와 별개의 **기본 합성·아트디렉션·컨트롤 품질 게이트 실패**다. 앞으로 확장 UI 검수는 두 번 수행한다. 첫 패스는 사용자가 지목한 결함을 확인하고, 두 번째 패스는 그 지목을 잊고 전체 화면에서 불투명 매트, 자산 중복 의미, 그림체 일관성, 버튼 상태, 진행 정보의 실제 의미, 타이포 위계, 초점과 게임 고유성을 다시 판정한다. 어느 하나라도 명백히 무너지면 요청된 버그가 고쳐져도 화면은 거절한다.

이 규칙은 `.agents/skills/improve-taskbar-game-quality/`의 `quality-gates.md`와 `failure-patterns.md`에 반영했다. 현재 menu-v1은 **Rejected at basic presentation-quality and UI/UX gates**다.

### 2026-07-11 원본 보존과 런타임 채택의 혼동, 그리고 검증 경로

사용자는 앞선 작업표시줄 고양이가 최초 콘셉트에서 거의 새로 만든 수준까지 발전한 사례를 들어, 메뉴 이미지 역시 대략적 콘셉트라면 필요할 때 버리고 레퍼런스를 기준으로 새로 만들어야 했다고 지적했다. 이 지적은 맞다.

- 프로젝트의 `보존` 규칙은 원본·출처·실패 증거를 삭제하지 말라는 뜻이다. rejected/superseded/concept 파일을 화면에 계속 붙여 두라는 뜻이 아니다.
- Codex는 이미 통합한 비용을 아끼려는 방향으로 crop, `cover/contain`, 배경색, 테두리, 슬롯 크기를 반복 조정했다. 이는 품질이 낮은 핵심 자산을 교체하지 않고 주변 CSS가 책임지게 한 sunk-cost 경로다.
- 현재 menu-v1 자산은 소스와 실패 증거로 보존하되 IP-holder/Steam 제안용 런타임 후보에서는 제거한다. 다음 자산은 레퍼런스 보드와 하나의 시각 언어를 먼저 정하고, 투명 배경·역할별 구도·버튼 상태·실제 합성 화면을 승인받은 뒤 파생한다.

검증도 하나의 자동 브라우저 경로와 전체 검증을 동일시하면 안 된다.

- 직접 가능한 검증: 원본·알파·매트·가장자리·실제 배경 합성, 아이콘/버튼/상태 접촉표, 실제 표시 크기, 화면 전체 스크린샷, 해시/매니페스트/상태 불변식.
- 사용자 제공 증거로 가능한 검증: 현재 실제 창의 정적 조합, crop, 겹침, 시각 위계, 버튼/아이콘 합성. 이번 메뉴 문제는 이 경로만으로도 충분히 거절할 수 있었다.
- 라이브 증거가 별도로 필요한 항목: 최종 속도 애니메이션, hover/pressed/drag/toggle, 전환 타이밍, 입력 반응. 해당 항목만 `Implemented, not verified`로 남겨야 한다.
- 다른 브라우저/컴퓨터 캡처 표면은 그 표면의 정책과 사용자의 선택이 허용할 때만 사용한다. 선택된 도구가 다른 표면 우회를 금지했다면 설치나 별도 자동화로 정책을 우회하지 않는다.
- 안전한 의존성 설치는 허용된 QA 능력을 추가할 때 사용한다. 설치는 플랫폼 보안 정책을 해제하는 수단이 아니다.

이번에 공식 Codex 매뉴얼 도우미는 기본 캐시와 `%TEMP%` 캐시 모두 `Manual response is missing x-content-sha256`로 실패했다. 공식 OpenAI 문서 MCP를 추가하려 했으나 WindowsApps 패키지의 `codex.exe` 실행 단계에서 `Access is denied`가 발생했다. ACL 변경이나 시스템 정책 약화는 시도하지 않았고 설치는 완료되지 않았다. 이 문서 연결 실패는 프로젝트 이미지·스크린샷 검증을 막는 요인이 아니다.

품질 스킬에는 `보존 ≠ 런타임 유지`와 `한 캡처 표면 차단 ≠ 모든 검증 차단` 규칙을 추가했다. 공식 validator와 collector self-test를 통과했고, 독립 forward-test도 콘셉트 자산을 런타임에서 제거하고 정적·자산·사용자 캡처 검증을 계속하되 라이브 동작만 별도 미검증으로 남기는 경로를 선택했다.

### 다시 사용하지 않을 경로

- 같은 네 포즈의 속도와 간격만 다시 조절하는 방식.
- 밀가루, 별, 하트, 티켓 같은 FX를 더 많이 붙여 생명감을 대신하는 방식.
- 앞발 셀만 더 무작위로 교체하는 방식.
- 기존 실패를 되살리는 전신 CSS 바운스·회전·좌우 흔들기.
- 비대칭과 운동 사슬 없이 또 다른 독립 전신 프레임 묶음을 생성하는 방식.

### 채택할 다음 제작 경로

1. 같은 캐릭터·복장·품질을 유지하되 몸이 반죽 쪽으로 아주 약간 기울고 좌우 무게가 다른 **한 장의 rig-ready 작업 중립 마스터**부터 만든다.
2. 128px 밝은/어두운 배경에서 실루엣, 표정, 두 앞발 접촉과 작업표시줄 부착감을 사용자에게 먼저 승인받는다.
3. 작업대/골반 루트는 고정하고 머리+시선, 귀, 꼬리, 몸통, 좌우 상완/전완/앞발, 얼굴, 반죽 접촉을 겹침 여유가 있는 레이어로 분리한다.
4. 첫 동작은 한쪽 누르기 하나만 만든다: 시선·고개가 먼저 반죽을 보고, 어깨/전완/앞발이 연결돼 눌리며, 반죽이 반응하고, 몸이 같은 루트로 복귀한다.
5. 이 한 동작을 실제 128px 속도로 승인받기 전에는 idle·반대 손·완료·마우스 추적을 확장하지 않는다.

### 귀 파닥과 모자 지연 추종 요구

사용자는 살아 있는 느낌을 위해 귀가 짧게 파닥이고 모자도 그 움직임에 맞춰 살짝 따라와야 한다고 추가로 짚었다. 이는 장식 추가가 아니라 운동 사슬의 2차 동작 요구로 분류한다.

- 좌우 귀는 머리 뒤의 별도 레이어로 분리하고 각 귀 기저부를 충분히 겹쳐 회전 이음새가 드러나지 않게 한다.
- 귀 동작은 시선 전환, 사용자 쪽 주의, 접촉 직전 긴장 또는 드문 idle 반응에 연결한다. 매 누름마다 양쪽 귀가 같은 크기로 파닥이는 반복 루프는 사용하지 않는다.
- 모자는 `머리 → 모자 밴드 → 유연한 크라운/주름` 계층으로 둔다. 밴드는 머리와 1:1로 움직이고 크라운만 짧은 지연과 작은 오버슈트로 따라온다.
- 모자 전체가 머리와 분리돼 뜨거나, 귀와 모자가 앞발과 무관하게 계속 흔들리거나, 128px에서 외곽선이 흐려지는 결과는 실패다.
- 첫 한쪽 누르기 증명판에서는 머리·시선이 먼저 움직이고, 한쪽 귀가 짧게 반응하며, 머리에 붙은 모자 윗부분이 약간 늦게 정착하는지만 본다. 정확한 각도·픽셀·지연값은 아직 검증 전이며 실제 128px 연속 재생에서 조정한다.

현재 빠른 게임감 v1의 캐릭터 생명감 판정은 **Rejected by user**다. 진행 티켓·저장 마이그레이션·드래그·메뉴 토글의 기능적 구현은 증거로 보존하지만, 기존 네 포즈에 FX와 타이밍을 더하는 경로는 종료한다.

현재 상태는 **Implemented, not live-verified**다. 정지 QA와 자동 계약은 통과했지만, 열린 `file:` 페이지의 실제 연속 재생에서 fast/overdrive의 타격 리듬과 sniff의 의미가 자연스러운지는 사용자가 새로고침 후 판단해야 한다.

## 27. 2026-07-10 접촉 충격 크라운과 밀가루 펑펑 강화

사용자는 직전 버전도 밀가루가 약하고 타격감이 부족하다고 판정했다. 손 모션을 더 크게 해도 접촉 이펙트가 약하면 반죽 위에 손을 대는 느낌일 뿐이라고 명시하고, 큰 흰 충격 덩어리와 바깥으로 터지는 선이 있는 만화식 참고 이미지를 제공했다.

### 진단과 범위

- 직전 버전은 3.14px의 안전한 손 이동과 국소 반죽 눌림을 확보했지만, 접촉 프레임의 실루엣과 원거리 가루 양이 작아 실제 재생에서 `펑`의 피크가 약했다.
- 참고 이미지의 검은 잉크·`쾅` 글자를 복사하면 요리/밀가루보다 전투 폭발로 읽히고 112px 고양이를 덮는다. 구조적 언어만 가져와 따뜻한 밀가루 재질로 번역한다.
- 고양이 크기, 손 이동 3.14px, 입력 임계값, 보상, 메뉴, sniff와 나머지 idle은 변경하지 않는다.

### 수정

- 손 뒤에 합성하는 `impact_back_fx`를 추가했다. fast는 최종 표시 약 21.4px의 단일 톱니형 반원 크라운, overdrive는 약 27.7px의 이중 크라운을 사용한다.
- 크라운은 cocoa 외곽+따뜻한 flour-white 중심이며, 손과 팔은 그 위에 다시 그려 접촉 해부가 보이게 한다.
- 손 앞에는 fast 연결 구름 4개와 공중 가루 7개, overdrive 연결 구름 9개와 공중 가루 14개를 배치한다. 대각선 청록 속도선과 국소 반죽 압축은 유지한다.
- 밀가루 로브는 하나의 union mask로 합쳐 외곽선을 구름 전체에 한 번만 적용한다. 작은 원마다 테두리를 두르지 않는다.
- CSS 자산 캐시는 v14로 올리고 새 WebP 해시를 단일 HTML 품질 게이트와 회귀 테스트에 등록했다.

### 실패와 우회

- 첫 overdrive 빌드는 왼쪽 접촉점의 +76도 방사선이 아래로 길게 뻗어 고정 반죽 루트 영역을 변경했다. 동일 빌드를 반복하거나 루트 게이트를 줄이지 않고, overdrive 방사선을 -116~+38도의 위/바깥 부채꼴로 제한해 루트 변경 0을 회복했다.
- 첫 112px 시트는 각 퍼프마다 cocoa 테두리가 생겨 큰 이펙트가 꽃·비눗방울 무리처럼 보였다. 크기만 줄이거나 색만 바꾸지 않고 모든 로브를 하나의 불규칙 구름 실루엣으로 합성하는 방식으로 변경했다.
- 손 이동을 다시 키우는 경로는 사용하지 않았다. 직전의 3.83px/3.42px 관통 실패와 사용자의 이번 지시를 함께 반영해, 타격 피크·구름 면적·가루 밀도만 보강했다.

### 검증과 판정

- fast SHA-256 `16dbf8bf994d1fbeee15129225b0b032e3b16b5f4f8fb9e8cfccc9f377e3015f`; overdrive `08678c4b0903a74ac84a0d2d4e249313d8ffffc923f19796966a1bfa95565a64`.
- 두 모드 모두 첫/끝 동일, 고정 반죽 루트 변경 0, 보이는 초록 우세 픽셀 0, 투명 모서리, 1,000ms duration과 6/8접촉/초를 통과했다.
- 112px light/dark 시트와 checker 접촉표에서 fast/overdrive 크기 차이, 손 뒤 크라운, 연결된 밀가루 구름, 손/얼굴 가독성과 한 반죽을 직접 검토했다.
- 첫 최종 시트의 fast 샘플은 실제 최대 접촉이 아닌 약 34.7% 접촉의 frame 11이라 전달된 효과를 축소해 보여줬다. 시트 생성기를 실제 최대 접촉 frame 1(약 99.1%)로 고치고 112px light/dark에서 손 가림·밀가루 재질·크라운 크기를 다시 통과시켰다.
- Node `34/34`, JS/Python 문법, manifest/해시/FX 계약, 단일 HTML Base64 round trip과 `--check`가 통과했다.
- 단일 HTML은 22,972,743 bytes, SHA-256 `57399b77ac61d79c16d85ed2010467171cd74fbc037d7af0abc5723aa42664ba`, 내장 자산 27개다.
- Pillow 12.3.0, NumPy 2.2.6, OpenCV-headless 4.12.0.88은 `tmp/impact-powder-tools`에만 임시 설치했고 생성 후 절대경로를 확인해 제거했다.

품질 스킬의 기존 교훈을 `FX가 모션을 대신할 수 없다`에서 **세 타격 채널 중 어느 하나도 다른 둘을 대신할 수 없다**로 좁혔다. 안전한 손 이동과 반죽 반응이 있어도 FX 피크가 작으면 실패하며, 개별 원형 퍼프가 꽃/버블로 읽히면 구름의 union 실루엣으로 바꾼다. 스킬 validator와 collector self-test는 통과했다.

새 결론을 주지 않은 read-only forward-test는 현재 자산의 22개 선언 해시, 20×50ms/25×40ms 구조, 한 반죽·연결된 두 앞발·접촉 중심·flour/cocoa 재질·fast/overdrive 단계 차이에 정지 차단 결함이 없다고 독립 판정했다. 동시에 50/40ms 피크가 실제 재생에서 펀치가 아니라 깜빡임으로 보이는지, 손·반죽 압축·밀가루가 동기화되는지는 연속 재생만 증명할 수 있다고 했다. 약할 경우 이동/입자를 더 키우지 않고 접촉·압축·크라운 피크를 감쇠 프레임 하나만큼 연장하는 것이 다음 안전 우회다.

forward-test의 디코딩 검사는 source root 변경 0과 별개로 128→112 Lanczos 축소에서 보호 영역 상단의 RGB만 fast 26px/overdrive 31px, 최대 채널 차이 13까지 변할 수 있음을 찾았다. 알파·실루엣·하단선은 0 변화라 기하학적 루트 이동은 아니지만 색 반짝임 가능성을 미검증 제한으로 남긴다.

현재 상태는 **Implemented, not live-verified**다. 정지 프레임의 크기·재질·루트 안전은 통과했지만, 사용자가 열린 112px `file:` 페이지에서 fast가 한 번 크게 `펑`, overdrive가 연속 `펑펑`으로 읽히는지는 새로고침 후 연속 입력으로 판단해야 한다.

## 28. 2026-07-10 실제 재생에서 타격 FX가 보이지 않음

사용자는 새 버전을 실제 열린 단일 HTML에서 본 뒤 `조금 부족해 안 보여`라고 판정하고, Codex가 직접 화면을 보면서 조정하는지 물었다. 이 사용자 판정은 112px 정지 시트·해시·내부 검토보다 우선한다. 현재 fast/overdrive 타격 가시성은 승인되지 않았다.

Codex가 실제로 본 것은 생성된 소스/디코딩 프레임, checker 접촉표와 112px 정지 피크 시트였으며, 사용자의 연속 재생 화면은 보지 못했다. 정지 피크는 21.4/27.7px 크라운을 보여도 50/40ms로 지나가 실제 재생에서는 깜빡임처럼 소실될 수 있다.

사용자의 질문 뒤 `browser:control-in-app-browser`로 현재 열린 정확한 `file:///.../taskbar-cat-hero-single.html` 탭을 열거하고 claim했지만, 첫 screenshot 단계에서 URL 보안 정책이 거부했고 localhost·다른 브라우저·간접 실행·원시 명령 우회를 명시적으로 금지했다. `docs/workaround-ledger.md`에는 같은 환경과 거부가 이미 기록돼 있었으므로, 이번 재시도는 기존 우회 기록을 먼저 적용하지 못한 절차 오류다. 거부 뒤에는 어떤 우회도 시도하지 않았다.

다음 수정 전 필요한 근거는 사용자가 빠르게 타이핑하는 2~3초 화면 녹화 또는 GIF다. 그 캡처에서 접촉 피크의 실제 보이는 프레임 수, 손/반죽/밀가루 동기화, fast와 overdrive 구분을 확인한 뒤 dwell·불투명도·발생 빈도를 조정한다. 추가 자료 없이 다시 크기·입자 수·손 이동을 추측해 키우는 경로는 중단한다.

현재 상태는 **Cannot judge completion / current live visibility rejected**다. 구현 파일과 자동 테스트는 유지되지만 타격감 요구는 충족됐다고 말할 수 없다.
